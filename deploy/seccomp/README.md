# Seccomp profile for the API container

PDF exports run Chromium with **its own sandbox on** (`chromium_sandbox=True`; never `--no-sandbox`). On Linux that sandbox puts each renderer into new user, PID and network namespaces and `chroot`s it into an empty directory. Then it adds its own seccomp-bpf filter on top.

Docker's default seccomp profile only allows the namespace calls to containers that hold `CAP_SYS_ADMIN`, and `chroot` only to containers that hold `CAP_SYS_CHROOT`. FinPilot drops every capability, so under the default profile Chromium can't start its sandbox. In that case the export fails closed (503 `pdf_unavailable`).

| File | What it is |
|---|---|
| `docker-default-29.9.2.json` | Docker's own default profile, byte for byte. It's the version vendored by Docker Engine 29.9.2 (the server's), from `moby/moby` tag `docker-v29.9.2`, `vendor/github.com/moby/profiles/seccomp/default.json` (moby/profiles v0.2.4), sha256 `785b2429…9334` |
| `api-chromium.json` | That profile, with `clone`, `unshare` and `chroot` allowed without the capabilities, and Docker's two argument-filtered `clone` rules removed so no call has two rules. Generated by `build_profile.py`, never edited by hand |
| `build_profile.py` | Regenerates it; `--check` fails if it's out of date. `backend/tests/test_deploy_config.py` runs the check and checks the difference |

**Scope:**
- Only the `api` service uses this profile (`compose.yaml`; `scripts/lib.sh` passes its absolute path). Every other container keeps Docker's default.
- No capability is added. `no-new-privileges` stays on, and the root filesystem stays read-only.

**Trade-off, stated plainly:** any process in the API container can now create user namespaces. That's a larger kernel attack surface than the default profile allows, and it's the price of keeping Chromium's sandbox. The alternatives are worse:
- `--no-sandbox` removes the renderer sandbox entirely;
- `CAP_SYS_ADMIN` grants far more;
- `seccomp=unconfined` drops all syscall filtering.

A later improvement is a separate rendering container, so the API process itself never needs this.

**Verification:**
- `deploy/scripts/stack-test.sh` runs `python -m scripts.sandbox_probe` under:
  1. Docker's default profile (expected to fail);
  2. this profile;
  3. this profile with AppArmor relaxed, as a diagnostic only, in a throwaway container with no network, and only if step 2 fails.
- It runs the same probe inside the running API container, and checks that every PDF export succeeds.
- The probe passes only when no Chromium process carries `--no-sandbox`, and every renderer is in its own PID namespace under an extra seccomp filter.
